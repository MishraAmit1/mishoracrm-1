1Ek nazar mein — the material pipeline

Ye stack ek chhoti se mid manufacturing company ka pura "material lifecycle" cover karta hai: material maangna → kharidna → quality check ke saath receive karna → sahi cost ke saath stock mein daalna → usse production karna → finished goods → bechna. Saath mein purchase-side ka paisa (vendor ko kitna dena hai) aur GST compliance.

Chhoti company vs mid company — kaun kya use karega

LayerChhoti company (1–15 log, 1 location)Mid company (15–150 log)
Procurement (PR / PO / GRN)PR shaayad skip; PO + GRN directlyPoora chain — PR approval, vendor quotes, QC
Costing & batchesWeighted-avg cost + low-stock alert kaafiSame + inventory valuation reports
ProductionBOM + simple Work Order; stages optionalStages/routing, reservation, scrap tracking
Accounts PayableBill + payment record; approval nahiBill + payment + (roadmap) approval limits
GSTAuto CGST/SGST (mostly local sales)CGST/SGST + IGST inter-state

Bottom line: jo aaj shipped hai wo ek chhoti-mid manufacturer ke liye end-to-end kaam karta hai. Roadmap items mostly tabhi chahiye jab company mid-size ho ya specific industry (serialised high-value goods, multi-plant).

A · Procurement

Purchase Requests (PR) shipped

Kya
Andar se koi bhi "mujhe ye material chahiye" ki request daalta hai. Approver haan/naa karta hai; approve pe ek draft Purchase Order apne aap ban jaata hai.
Kyun
Kharidne se pehle authorization ka ek step — kaun maang raha hai, kis department ke liye, kyun. Bina iske har koi seedha vendor ko order bhej deta.
Kaha / Kab
Pipeline ka pehla step. Shop floor / stores / production planner PR banata hai; purchase manager approve karta hai.

Data

  • purchase_requests — number, department_id, items json, status, approved_by

Screens

  • tenant.purchase-requests.*
  • index / create / show / approve / reject

Tests

  • PurchaseRequestCrudTest

Purchase Orders + Vendor Quotes shipped

Kya
Vendor ko formal order. Ek draft PO ke against 2–3 vendors ke quotes daal ke compare kar sakte ho, sabse achha pick karo — uske rates PO pe apply ho jaate hain. PO PDF ban ke email ho jaata hai.
Kyun
Vendor selection transparent (rate comparison record), aur ek clean document jo vendor ke paas jaata hai. Received quantity isi PO ke against track hoti hai.
Kaha / Kab
PR approve hone ke baad (ya directly). Draft → vendor set → Sent → goods aane par receive.

Data

  • purchase_orders — vendor_id, purchase_request_id, items json, subtotal/discount/tax, status
  • vendor_quotes — per-vendor rates against PO lines

Screens

  • tenant.purchase-orders.*
  • PDF, email to vendor, Excel export

Tests

  • PurchaseOrderCrudFlowTest, VendorQuoteTest

Goods Receipt Note (GRN) + Quality Inspection is round

Kya
Har delivery = ek GRN. Har line pe Received / Accepted / Rejected + reason. Sirf accepted quantity stock aur cost mein jaati hai; rejected qty GRN pe aur PO line ke rejected_quantity pe log hoti hai.
Kyun
Pehle receive karte hi poori qty stock mein aa jaati thi — defective maal bhi. Real factory mein QC step hota hai: 100 aaye, 92 pass, 8 reject. Rejected qty ka record vendor follow-up / debit note ke liye chahiye.
Kaha / Kab
Jab vendor ka truck aata hai. Store keeper GRN banata hai; QC accepted qty decide karta hai.

Data

  • goods_receipt_notes — number, received_date, items json {received / accepted / rejected / reason / batch / expiry}

Screens

  • PO show → "Goods Receipt (GRN)" form
  • tenant.purchase-orders.grns.show

Tests

  • GoodsReceiptTest

B · Inventory & Costing

Weighted-Average Costing is round

Kya
Har product pe ab cost_price (weighted moving average) alag hai rate (selling price) se. Jab bhi PO se stock receive hota hai, us line ke rate se cost roll-forward hota hai: (oldQty×oldCost + inQty×inRate) / newQty.
Kyun
Pehle BOM / Work Order costing raw material ke selling rate ko cost maan raha tha — galat. Production cost aur inventory valuation dono galat aate the. Ab actual paid rate cost banta hai.
Kaha / Kab
Automatic — GRN accept, Work Order complete. Manual override product form pe.

Data

  • products.cost_price, product_batches.unit_cost

Screens

  • Product form "Purchase Cost / Unit"
  • Products list "Cost" col + "Stock Value (at cost)"

Tests

  • InventoryCostingTest

Batch Tracking (FEFO) + Expiry Alerts shipped

Kya
Jab bhi stock aata hai (GRN ya Work Order), ek batch banta hai — batch number, received date, optional expiry. Consumption FEFO (First-Expiry-First-Out) hota hai: sabse pehle expire hone wala batch pehle use hota hai.
Kyun
Traceability (kaunsa lot kis order mein gaya) aur perishables / chemicals / food ke liye expiry management. Ek daily command expiring batches pe tenant admin ko alert karta hai.
Kaha / Kab
Automatic har receipt / consumption pe. Product → "Batches" page pe ledger dikhta hai.

Data

  • product_batches — batch_number, quantity, initial_quantity, unit_cost, expiry_date, purchase_order_id / work_order_id

Screens

  • tenant.products.batches
  • command products:check-batch-expiry

Tests

  • ProductBatchTest

Low Stock + BOM Reorder Suggestions shipped

Kya
Har product pe reorder level + reorder quantity. Jab stock line cross karta hai, tenant admin ko notification. Low Stock page se ek click pe pre-filled Purchase Request — finished good ke liye uska BOM explode ho ke raw materials suggest hote hain.
Kyun
Stockouts se production rukti hai. Reorder suggestion se procurement ko manually BOM calculate nahi karna padta.
Kaha / Kab
Continuous — har sale / consumption ke baad check. Sidebar → Purchase → Low Stock.

Tests

C · Production

Bill of Materials (BOM) shipped

Kya
Har finished good ke liye "1 unit banane mein kya-kya lagta hai" — raw material + quantity per unit. Product edit page pe define hota hai.
Kyun
Production planning, material requirement, aur costing sab BOM pe khade hain. BOM ke bina Work Order ko pata nahi kya consume karna hai.
Kaha / Kab
Product setup ke time. Ek baar define, har Work Order use karta hai.

Example

Steel Chair (finished good)
  Steel Rod       × 5   (per chair)
  Cushion         × 1
  Screws          × 8

WO of 10 chairs → 50 rod, 10 cushion, 80 screws needed.

Data

  • bill_of_material_items — product_id (finished), material_id (raw), quantity_per_unit

Work Orders shipped

Kya
Ek production job: "10 × Steel Chair banao". Material shortfall check, stock consumption, cost snapshot (material + labor + machine), margin vs selling price.
Kyun
Production ko track karne ki central entity — kya ban raha hai, kaun laga hai, kitna cost aaya, profitable hai ya nahi.
Kaha / Kab
Jab production planner decide karta hai batch banana hai. Gated behind the "Manufacturing" module toggle.

Lifecycle ab reservation, WIP, stages aur scrap se enrich ho gaya hai — agla diagram poora picture dikhata hai.

Data

  • work_orders — product_id, quantity, produced_quantity, scrap_quantity, status, *_at, labor/machine/material cost

Screens

  • tenant.work-orders.* (module-gated)

Material Reservation + WIP is round

Kya
WO create pe BOM materials reserve ho jaate hain (physical stock nahi hilta, sirf available-to-promise girti hai). WO start pe materials issue hote hain — FEFO consume + reservation release, aur material cost yahin freeze. Ye WIP hai: material gaya, finished good abhi nahi.
Kyun
Pehle material sirf completion pe consume hota tha (all-or-nothing). Do pending WO dono feasible dikhte the, phir ek stock kha leta, doosra fail. Reservation ye race khatam karta hai.
Kaha / Kab
Reserve → auto on create. Issue → "Start & Issue Materials" button. Cancel → WIP ho to material wapas stock, warna sirf reservation release.

Data

  • products.reserved_stock (available = current − reserved)
  • work_orders.materials_issued_at

Tests

  • WorkOrderWipTest

Production Stages / Routing is round

Kya
WO ke andar ordered steps — Cutting → Welding → QC → Packing. Har stage pe assigned worker + status (pending / in progress / done / skipped) + start/complete time. WO create/edit form pe stage rows.
Kyun
Pehle ek flat status tha. Multi-step production mein pata nahi chalta job kahan atki hai, kis stage pe kitna time laga. Ab WO complete tabhi hota hai jab har stage done/skipped ho.
Kaha / Kab
Stages sirf tab actionable jab WO in progress (materials issued). Stage-less WO bilkul pehle jaisa (single start→complete) — optional feature.

Data

  • work_order_stages — sequence, name, assigned_to, status, started/completed_at

Tests

  • WorkOrderStagesTest

Scrap / Yield is round

Kya
WO complete pe Produced (good) + Scrap + reason enter hota hai. quantity = planned run (material consumption drive karta hai); sirf produced qty finished-good stock mein credit hoti hai.
Kyun
Pehle 10 ka WO hamesha exactly 10 finished goods deta tha. Real production mein rejection / wastage hoti hai. Poore run ka cost good units absorb karte hain — scrap se cost/unit badhta hai (correct costing).
Kaha / Kab
Completion screen pe. Total scrap (0 produced) bhi valid — materials phir bhi consumed, batch contamination waghera.

Example — cost absorbs scrap

Planned 10, material cost ₹3000
  No scrap:  ₹3000 / 10  = ₹300 per unit
  2 scrap:   ₹3000 / 8   = ₹375 per unit  ← good units carry it

Data

  • work_orders.produced_quantity / scrap_quantity / scrap_reason; WorkOrder::yieldQuantity()

E · Compliance

GST — CGST / SGST / IGST Split is round

Kya
Har tax doc (Quotation, Invoice, Purchase Order, Vendor Bill) pe place_of_supply, is_inter_state, cgst_amount, sgst_amount, igst_amount. Same state → CGST+SGST (aadha-aadha); alag state → full IGST. tax_amount still = total.
Kyun
Pehle ek flat GST line thi — GST-compliant invoice nahi. Ab place-of-supply logic proper hai.
Kaha / Kab
Automatic doc save pe. Sales: supplier = tenant company state (settings['state']), recipient = customer. Purchase: supplier = vendor, recipient = tenant. Show pages + PDFs proper split dikhate hain.

Data

  • 5 cols × quotations / invoices / purchase_orders / vendor_bills

Known gap

0Contact state dropdown + place-of-supply warning

Kya: GST feature ne vendor form ka state dropdown bana diya, par contact (customer) form abhi bhi free text hai (complex JS-driven form). Agar customer ka state ya GSTIN blank ho, ya typo ho ("karnatka"), to place-of-supply resolve nahi hota → galat CGST/SGST/IGST → non-compliant invoice jo compliant dikhta hai.

Fix

1. Contact create/edit form mein state ko config('crm.states') dropdown banao. 2. Invoice/Quotation save pe agar recipient state + GSTIN dono blank hon to ek soft warning: "Place of supply not set — GST split assumed intra-state." 3. Ek data-fix command purane contacts ke free-text state ko codes mein normalize kare (vendor migration jaisa).

Effort XSFiles: 2 blade + 1 request + 1 commandRegression risk low

Kaun: koi bhi tenant jo GST invoice bhejta hai. Do this first — compliance bug hai.

1Multi-level BOM (sub-assemblies)

Kya: Abhi BOM ek level explode hota hai: finished good → raw materials. Agar koi "raw material" khud manufactured hai (apna BOM rakhta hai), wo recursively handle nahi hota.

Real example — Steel Almirah

Almirah (finished good)
├─ Door Assembly   (sub-assembly — apna BOM)
│  ├─ Steel Sheet 2mm × 1.5
│  ├─ Hinge × 3
│  └─ Handle × 1
├─ Frame Assembly  (sub-assembly)
│  ├─ Steel Angle × 4
│  └─ Welding Rod × 0.2 kg
└─ Lock × 1

Abhi: Door Assembly aur Frame Assembly ke liye alag Work Orders manually. System nahi samajhta ki Almirah banane se pehle 2 sub-assemblies chahiye.

Proposed: bill_of_material_items.material_id khud ek finished/sub-assembly product ho sakta hai. BOM explosion recursive — jab shortfall check ya reserve/issue hota hai, sub-assembly ke liye ya to (a) uska stock use ho, ya (b) ek nested Work Order chain suggest / auto-create ho. Circular-BOM guard chahiye.

Data: koi nayi table nahi — StockService::productionShortfallFor, reserveForProduction, issueForProduction, consumeForProduction, WorkOrder::calculateLiveMaterialCost sab recursive banane padenge, ek depth limit + visited-set ke saath.

Effort LTouches: StockService, WorkOrderService, WO create UI

Kaun: Chhoti company — shaayad nahi (simple 1-level products). Mid — must have. Furniture, electrical panels, machinery, pumps, auto-parts — 2–4 level BOM common.

2MRP Aggregation (material requirements planning)

Kya: Reservation (gap #6) ne available stock dikha diya, par ek combined plan nahi banta. Har WO alag dekhna padta hai.

Real example — 5 open Work Orders

WO-1  10 Chairs  → 50 Steel Rod
WO-2  20 Tables  → 80 Steel Rod
WO-3  15 Chairs  → 75 Steel Rod
WO-4   5 Almirah → 30 Steel Rod
WO-5   8 Tables  → 32 Steel Rod
───────────────────────
Total needed  267 kg
On hand       100 kg
Net shortage  167 kg  → ONE consolidated PR/PO

Proposed: nayi read-only screen + service MrpService::plan($tenantId). Loop over pending/in-progress-not-issued WOs, BOM explode, aggregate per material, subtract (on-hand − reserved) + (incoming PO qty). Output: per-material net requirement. "Create PR" button consolidated PR banata hai. Koi schema change nahi.

Effort MBase ready (reservation done)New: 1 service + 1 screen

Kaun: Chhoti — nahi (1–2 WO, mentally calc). Mid — high value. 10–50 open WOs pe procurement team roz ye karti hai. Bina iske over-purchase (paisa block) ya production ruk.

3PO Approval Limits / Spend Authorization

Kya: PR pe approval hai, PO khud nahi. Jiske paas purchase_orders.create hai wo ₹10 lakh ka PO bhej sakta hai bina kisi review ke.

Real example — approval matrix

≤ ₹5,000       → executive self-approve
₹5k – ₹50,000  → manager approval
> ₹50,000       → director approval

Proposed: tenant settings mein approval thresholds (JSON). PO "Send" karne se pehle agar total > threshold ho → status pending_approval, approver ko notification (PR ke notifyApprovers pattern jaisa). Approve/reject actions. Draft PO edit ho sakta hai; approved PO lock.

Data: purchase_orders mein approval_status, approved_by, approved_at. Settings mein thresholds. Nayi permission purchase_orders.approve.

Effort SPattern exists (PR approval)

Kaun: Chhoti — nahi (owner sab dekhta hai). Mid — yes. 5–10 log procurement mein → audit, fraud prevention, budget control.

4Vendor Performance Dashboard

Kya: GRN data ab capture ho raha hai (received vs accepted vs rejected, delivery dates), par koi scorecard nahi.

Real example — vendor selection ke time

Vendor A  45 POs | on-time 92% | reject 2.1% | avg delay 1.2d
Vendor B  38 POs | on-time 71% | reject 8.4% | avg delay 6.5d
Vendor C  12 POs | on-time 100%| reject 0%   | avg delay 0d

Isse pata: Vendor B se bacho chahe rate kam ho.

Proposed: Vendor show page + ek "Vendors → Performance" list. Compute from GRN + PO: on-time % (received_date vs expected_delivery_date), rejection % (rejected / received across GRNs), avg delay, PO count, total spend. Sirf ek reporting query + UI.

Effort SData already capturedNo schema change

Kaun: Chhoti — nahi (3–4 vendors, yaad hote hain). Mid — high value. Data-driven purchase decisions + negotiation leverage. Achha ROI — data ready hai.

5Debit Notes

Kya: GRN pe rejected qty + reason log hoti hai, par vendor ko formal document nahi jaata.

Real example

Ordered 100 rod @ ₹100.  15 defective (GRN).
Vendor bill:  ₹10,000 (full 100)
Debit Note:   ₹1,500 (15 × ₹100) against vendor
              → pay less / adjust in next bill

Proposed: nayi vendor_debit_notes table (ya reuse vendor_bills with a type flag). GRN se generate: rejected lines × rate. PDF + email. Vendor Bill / outstanding pe adjust hota hai (negative payable). GST-compliant document.

Effort SBuilds on GRN + Vendor Bill (dono done)

Kaun: Chhoti — nahi (phone pe adjust). Mid — yes. GST compliance + accounts reconciliation.

6PR → Multiple PO Split

Kya: Ek approved PR → ek draft PO (hasOne, 1:1). Ek PR ke items alag-alag vendors se nahi kharid sakte.

Real example

PR: Steel Rod, Paint, Bolts
  Steel Rod → Vendor A (sasta)
  Paint     → Vendor B
  Bolts     → Vendor C
→ abhi: 3 alag PO manually, PR link tootega

Proposed: purchase_requests → hasMany(PurchaseOrder). Approve pe ek "split" UI: PR lines ko vendor-wise group karo, per group ek PO. PR status "converted" jab saari lines koi PO mein ho. Har PO PR se linked rehta hai.

Effort MData model change (hasOne → hasMany)

Kaun: Chhoti — workaround chalega (1–2 vendors). Mid — yes. Har material category ka alag preferred vendor.

7Serial Number Tracking

Kya: Abhi batch-level (FEFO) traceability. "Batch X se 50 units gaye." Per-unit serial nahi.

Real example — Generator company

Complaint: "Generator SN-2026-0453 kharab hai"
→ kaunse WO mein bana, kaunsa alternator/motor (unke serials),
   kaunsa customer, kab bika, warranty valid?, pehle service?
Batch se ye nahi milta — batch mein 50 the.

Proposed: product_units table (serial, product_id, work_order_id, batch_id, invoice_id, warranty_until, status). Serialised flag per product. WO completion pe N serial rows generate. Invoice line pe serial pick. Warranty / service history un pe.

Effort MNew table + WO + Invoice hooks

Kaun: Chhoti — nahi. Mid — sirf high-value / warranty-bound goods (generators, machinery, electronics, medical devices, pumps, engines). FMCG / consumables / hardware ko bhi nahi.

8Multi-warehouse / Location Stock

Kya: Har product ka ek global number (current_stock). Batch hai par batch kis godown / rack mein hai, nahi.

Real example — Pune factory + Mumbai warehouse

Steel Rod total 500 kg  =  Pune 300 + Mumbai 200
Mumbai se dispatch: system "500 available" dikhata hai,
  actual Mumbai mein 200.  Inter-location transfer track nahi.

Proposed: warehouses table + stock ko (product × warehouse) dimension pe le jaana — product_location_stock ya batches pe warehouse_id. Har stock query (shortfall, FEFO, reserve, low-stock) mein location filter. Stock transfer document (out of one, into another). Bada architectural change.

Effort LEvery stock query changes

Kaun: Chhoti — nahi (factory = store). Mid — sirf agar actual multiple branches / warehouses / depots (distribution companies, multi-plant). Single-location mid ko bhi nahi. Demand aane par hi banao.
